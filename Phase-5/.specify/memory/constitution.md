# Hackathon II Todo App Constitution - Phase V: Advanced Cloud Deployment

## Core Principles

### I. Phase V Scope & Purpose
This constitution governs Phase V only of the project; Phase V objective is to evolve the existing Kubernetes-deployed Todo application into a production-grade, event-driven, cloud-native system on DigitalOcean Kubernetes (DOKS) with advanced features, event-driven architecture, and full CI/CD; No application feature development is allowed without corresponding infrastructure changes; All deployment activities must strictly follow: sp.constitution → sp.specify → sp.plan → sp.tasks → sp.implement sequence; The system shall be designed for scalability, resilience, and automation.

### II. Cloud-Native Excellence
All systems shall be designed for the cloud from inception, never as an afterthought; Managed services (Kafka, PostgreSQL, Kubernetes) shall be preferred over self-hosted; Architecture shall optimize for cloud cost efficiency through auto-scaling and serverless patterns; Twelve-Factor Application methodology must be adhered to; Services must be stateless and horizontally scalable; Declarative infrastructure defined as code (Kubernetes manifests, Helm charts, Terraform) is mandatory; Services shall be designed for rapid startup and graceful shutdown.

### III. Event-Driven First Architecture
Events shall be first-class citizens in the system; All significant state changes shall emit events before persistence; Services shall communicate exclusively via events, never through direct API calls for core business logic; The system state shall be fully reconstructable from its event stream; Loose coupling mandate: services shall communicate only through events; Event sourcing readiness: all business logic shall be reconstructable from event streams.

### IV. Spec-Driven Development Mandate
No line of code shall be written without a specification existing first; Specifications shall be the sole authority on system behavior; All implementations must be generated by Claude Code from specifications; All specifications shall be updated within one hour of implementation changes; Specifications shall be structured as perfect prompts for Claude Code; Every feature, component, and infrastructure change must originate from a written specification.

### V. AI-Assisted DevOps Primacy
Claude Code shall be the primary executor of all code generation; All infrastructure operations shall use kubectl-ai, kagent, or Docker AI Agent (Gordon); No manual infrastructure changes shall be made; All code generation shall originate from Claude Code, never manual typing; All prompts shall reference specific specifications and include context from CLAUDE.md files; AI-Ops integration shall be used for all Kubernetes operations.

### VI. Security by Design
Security shall be implemented at every layer, from code to infrastructure; All endpoints shall require JWT authentication; User data shall be strictly isolated by user_id; All sensitive data shall be encrypted at rest; All communications shall use TLS; Database credentials shall be rotated monthly; No secrets shall be committed to version control; All external dependencies shall be scanned for vulnerabilities.

## Technology Standards

### VII. Technology Stack Proclamation
The following technologies are hereby established as the Official Stack of Phase V:

Core Development Stack:
- Frontend: Next.js 14+ with App Router, TypeScript, Tailwind CSS
- Backend: FastAPI, SQLModel, Python 3.13+
- AI Layer: OpenAI Agents SDK, Official MCP SDK
- Database: Neon Serverless PostgreSQL
- Authentication: Better Auth with JWT

Cloud-Native Stack:
- Container Runtime: Docker with Docker AI Agent (Gordon)
- Orchestration: Kubernetes (Minikube for local, DigitalOcean DOKS for cloud)
- Package Management: Helm Charts
- Service Mesh: Dapr (Distributed Application Runtime)
- Event Streaming: Kafka (Redpanda Cloud Serverless)

DevOps Stack:
- AI-Ops: kubectl-ai, kagent, Claude Code
- CI/CD: GitHub Actions
- Infrastructure as Code: Kubernetes manifests, Helm charts
- Monitoring: Prometheus metrics, structured logging, health endpoints

### VIII. Prohibited Technologies
No direct database connections in frontend: frontend shall only communicate with backend APIs; No hardcoded secrets: all secrets shall be stored in Kubernetes Secrets or Dapr secret stores; No manual infrastructure changes: all infrastructure changes shall be made through code; No monolithic services: each distinct business capability shall be a separate, independently deployable service; No self-hosted managed services: when available, managed services shall be preferred.

## Architectural Principles

### IX. Microservices Principles
Each service shall have one, and only one, reason to change; Services shall be deployable independently without coordinating with other services; Services may use different technologies as appropriate for their domain; Each service shall be responsible for a single business capability; Services shall be composed of loosely coupled microservices communicating via events.

### X. Dapr Integration Mandate
All inter-service communication shall use Dapr service invocation; All state shall be managed through Dapr state stores; All events shall be published through Dapr pub/sub; All secrets shall be accessed through Dapr secret stores; Dapr building blocks (Pub/Sub, State, Bindings, Secrets) shall be integrated and operational.

### XI. Event-Driven Design Rules
All events shall have: event_id, event_type, timestamp, source, data, metadata; Events shall be versioned and backward compatible; Event schemas shall be documented in AsyncAPI format; At-least-once delivery for business events; Exactly-once processing for critical operations; Dead letter queues for failed event processing; Events shall be published to Kafka (Redpanda) and consumed by interested services.

## Development Process

### XII. Spec-Driven Development Protocol
Specification hierarchy: Constitution (this document) → Specification → Plan → Tasks → Implementation; All specifications shall be written in Markdown with Purpose, Requirements, Acceptance Criteria, Implementation Notes; All specifications shall be stored in `/specs/phase5/` organized by category; Implementation workflow: Specification → Claude Code Review → Code Generation → Local Testing → Pull Request → CI/CD Pipeline → Staging Deployment → Production Deployment.

### XIII. Quality Assurance Mandate
Unit tests for all business logic; Integration tests for all API endpoints; End-to-end tests for critical user journeys; Performance tests for high-traffic endpoints; All code shall pass static analysis (flake8, mypy, eslint); Test coverage shall exceed 80% for backend services; All dependencies shall be regularly updated and scanned for vulnerabilities; Every service shall have a README.md with setup instructions; Every API endpoint shall be documented with OpenAPI/Swagger; Every configuration option shall be documented.

### XIV. State Management Governance
Services shall be stateless whenever possible; State shall be stored in external systems (database, Dapr state store, Kafka with compaction, Redis Cache) to allow scalability; State shall reside in Neon PostgreSQL, Dapr State Store, or Kafka with compaction; The system shall implement retries, circuit breakers, and timeouts.

## Deployment & Operations

### XV. Deployment Strategy
Environment segregation: Development (Local Minikube with Dapr), Staging (DigitalOcean DOKS with full integration), Production (DigitalOcean DOKS with production-grade configuration); Feature flags for all new functionality; Canary deployments for high-risk changes; Blue-green deployments for zero-downtime releases; Automated rollback on failure detection; Application shall run on DigitalOcean Kubernetes (DOKS) with custom domain and TLS.

### XVI. Monitoring & Observability Requirements
Application metrics: request rate, latency, error rate; Business metrics: tasks created, completed, overdue; Infrastructure metrics: CPU, memory, disk, network; Structured logging in JSON format; Correlation IDs for tracing requests across services; Log aggregation with centralized storage; Critical alerts: Immediate notification (PagerDuty/Slack); Warning alerts: Daily digest; Informational alerts: Weekly report.

### XVII. Disaster Recovery Provisions
Daily automated backups of databases; Point-in-time recovery capability; Regular backup restoration testing; Multi-zone deployment for critical services; Automatic failover for database clusters; Load balancing with health checks; Disaster recovery runbook for each service; Regular disaster recovery drills; Communication plan for service disruptions.

## AI-Assisted Development

### XVIII. Claude Code Usage Guidelines
All prompts shall reference specific specifications; Prompts shall include context from CLAUDE.md files; Prompts shall be versioned alongside code; Generate code from specifications; Review generated code for compliance; Test generated code thoroughly; Refine specifications if code doesn't meet requirements; Use kubectl-ai for Kubernetes operations; Use kagent for cluster analysis; Use Docker AI Agent (Gordon) for container optimization.

### XIX. Continuous Learning Mandate
Update specifications based on implementation learnings; Document patterns and anti-patterns discovered; Share knowledge across the development team; Regularly analyze and optimize slow queries; Implement caching where appropriate; Monitor and optimize resource usage.

## Validation & Acceptance Rules

### XX. Phase V Success Criteria
Features: All intermediate and advanced features (priorities, tags, search, recurring tasks, due dates) implemented and tested; Events: Kafka event streaming setup with producers and consumers for task events, reminders, and audit; Dapr: Dapr building blocks (Pub/Sub, State, Bindings, Secrets) integrated and operational; Deployment: Application running on DigitalOcean Kubernetes (DOKS) with custom domain and TLS; CI/CD: Automated CI/CD pipeline with GitHub Actions; Monitoring: Basic monitoring and alerting setup; Auto-scaling: Horizontal Pod Autoscaler configured for scalability.

## Out-of-Scope (Explicitly Forbidden)

### XXI. Prohibited Activities
- 🚫 Local-only deployment - must be cloud-native
- 🚫 Monolithic architecture - must be microservices
- 🚫 Direct database access from frontend
- 🚫 Hardcoded secrets in configuration
- 🚫 Manual deployment processes
- 🚫 Synchronous communication for core business logic
- 🚫 Self-hosted event streaming - must use managed service
- 🚫 No event-driven architecture - must implement events

Proposed amendments must be submitted as pull requests; amendments require approval from all team members; amendments shall be documented with rationale.

Versioning Policy: MAJOR for backward incompatible governance/principle removals or redefinitions; MINOR for new principle/section added or materially expanded guidance; PATCH for clarifications, wording, typo fixes, non-semantic refinements.

Compliance Review: All pull requests must be validated against this constitution. Automated checks should verify that code changes comply with the stated principles, particularly around security, deployment, and infrastructure requirements. CI/CD pipeline shall include compliance validation; security scanning on every pull request; architecture compliance validation.
